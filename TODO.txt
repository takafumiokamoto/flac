## decodeCodedNumber のテスト補強(9.1.6 に進む前に済ませる)

根拠: RFC 9639 Section 9.1.5 / Table 18。符号化手順は RFC 3629 Section 3 を拡張テーブルで使う。

### 1. テストハーネスの穴をふさぐ
- want.err == true のとき err == nil を明示的に失敗にする
  (今は「成功時は readCount >= 1 になる」ことに間接的に頼っているだけ)
- どのエラー分岐で落ちたか検証できるようにする(分岐ごとの sentinel error か、メッセージ部分一致)。
  現状 "first byte doesn't end with 0" ({0xF7, 0xFF}) は、0xF7 = 0b11110111 が
  4バイト形式 11110xxx の正当な先頭バイトなので、「先頭バイト不正」ではなく
  「入力切断」の分岐で通っている。名前どおりの分岐を踏ませるなら 0xFF を使う。

### 2. 正常系: Table 18 の全 7 行をカバー(今は 1バイト形式と、overlong な 2バイト形式のみ)
- RFC 9.1.5 の実例をそのまま使う: FE AF 9F B5 A3 B8 80 -> 51,000,000,000 (readCount=7)。
  RFC 本文にある唯一の完全なテストベクタ
- 各行の下限・上限(octets は Table 18 から自分で符号化して導出する):
  1B: 0x00       / 0x7F
  2B: 0x80       / 0x7FF
  3B: 0x800      / 0xFFFF
  4B: 0x10000    / 0x1FFFFF
  5B: 0x200000   / 0x3FFFFFF
  6B: 0x4000000  / 0x7FFFFFFF   (上限 = 2^31 - 1。frame number の上限と一致)
  7B: 0x800000000 / 0xFFFFFFFFF (上限 = 2^36 - 1)
- coded number の後ろにゴミバイトが続いても readCount 分しか読まないこと
  (フレームヘッダでは後続に 9.1.6/9.1.7/CRC-8 が続くため)

### 3. エラー系の網羅
- 空入力 len(b) == 0
- 先頭バイト 0xFF(Table 18 のどの形式にも該当しない)
- 先頭バイト 10xxxxxx(既存ケースで済み)
- 入力切断(必要長 > len(b))を複数の長さで
- 継続バイト不正が 3 バイト目以降でも検出されること(既存は 2 バイト目のみ)

### 4. 決めごと(テストの期待値が変わるので先に決める)
- overlong encoding を受理するか拒否するか。
  RFC 9639 は「RFC 3629 Section 3 の手順に従う」とし、RFC 3629 Section 3 には
  「デコーダは invalid sequence の復号から保護しなければならない (MUST)」がある。
  Table 18 上も 0x3F に 2バイト形式の行は存在しない。
  拒否に倒すなら既存ケース {0xC0, 0xBF} -> 0b111111 は「エラー」に変わる。
  受理するなら RFC 3629 からの逸脱(寛容デコード)として方針をコメントに残す。
- fixed block size(frame number)のとき 31 bits / 6 bytes 超の扱い。
  9.1.5 の MUST NOT は符号化側への規定で、デコーダの挙動は未規定 -> 拒否するかは実装方針。
  検査するなら blocking strategy を知っている readFrameHeader 側(readCount == 7 で判定可)。

### 5. readFrameHeader 側の宿題(次のステップの前提)
- decodeCodedNumber の戻り値を捨てない: h.codedNumber へ格納し、
  読了バイト数を 9.1.6 uncommon block size / 9.1.7 uncommon sample rate / 9.1.8 CRC-8 の
  オフセットとして使う
- 継続バイトの取り出しマスク 0x7F を 0x3F(下位 6 bit)へ。
  直前の 10xxxxxx 検査があるから偶然同値になっているだけで、意図は 6 bit
- typo / 文法: "positoin" -> "position"、"second byte doesn't start with 0b10" は
  3 バイト目以降にも出るので "continuation byte ..." に、"4bytes" -> "4 bytes"、
  "first 15bits ... doesn't match" -> "first 15 bits ... don't match"(主語が複数)
- 変数名 payloadLength は実態が「シーケンス全長(バイト数)」なので改名を検討

### 6. ラウンドトリップ(元 TODO の取り込み)
- 符号器を書いて encode -> decode の一致を確認する。
  ただし自作同士の往復は内部整合性しか保証しないので、2. の固定ベクタを錨にする。
- 余力があれば go test -fuzz で「decode 成功なら encode(val) == 入力先頭 readCount バイト」を
  性質として回す(overlong を受理する実装だと自動で矛盾が出る)
